# 입문자용 KBO 야구 규칙 설명 에이전트 — 설계서 v1 (Phase 1)

작성 기준일 2026-09-15. 수치는 전부 이 저장소에서 실행해 측정한 값이다.

## 1. 목적과 사용자
- 야구를 처음 보는 사람이 "지금 무슨 일이 일어난 건지" 이해하도록, **2026 공식야구규칙(KBO·KBSA)** 을 근거로 답하는 웹 에이전트.
- 근거 없는 답을 하지 않는 것이 1순위. 규칙집·리그 규정 스냅샷·웹 검색 결과 중 **제공된 자료에 없으면 거부**한다.

## 2. 범위
- Phase 1(이 문서): 질문형 규칙 설명 + 최신정보(리그 규정 스냅샷·웹 검색) 경로.
- Phase 2(계획): YouTube 하이라이트, KBO 구단 정보(연고지·승률·선수 명단), 남은 경기 일정.

## 3. 아키텍처와 "에이전트" 범위 결정
```
Streamlit(8501) ──SSE──▶ FastAPI(8000) ──▶ HybridRetriever ──▶ pgvector(55432)
                                   │                └─ Kiwi BM25(인메모리)
                                   ├─ latest_info(YAML 스냅샷 + Tavily)
                                   └─ ChatOpenAI gpt-4o-mini (verbatim 프롬프트 1회)
ingest: data/*.pdf ─▶ MinIO(59000) ─▶ pymupdf ─▶ 구조 청킹 ─▶ text-embedding-3-large@1024 ─▶ pgvector
```
- Phase 1의 "에이전트"는 **결정적 retrieve-then-generate 체인**으로 구현했다. LangChain v1 문서가 FAQ·문서 봇에 이 패턴을 권장하고, 강의 자료도 LangGraph를 "시리얼 체인의 한계 이후" 단계로 배치한다.
- Function Calling 역량은 `src/baseball/tools.py` 의 `@tool` 2개(`search_baseball_rules`, `league_regulation_lookup`)와 `python -m baseball.tools demo`(bind_tools → `if ai_msg.tool_calls:` 4단계 루프)로 증빙한다. Phase 2에서 같은 도구를 에이전트에 넘긴다.

## 4. 상태 관리
- **Sliding Window(최근 8메시지)**: 규칙 Q&A는 짧은 문답이 대부분이고 비용이 예측 가능해야 하므로 요약·엔티티 메모리 대신 고정 창을 택했다.
- 구현: `dict[session_id, deque(maxlen=CHAT_HISTORY_MAX_MESSAGES)]`. 프롬프트에는 `MessagesPlaceholder("chat_history", optional=True, n_messages=8)` 로만 들어가며 **프롬프트 본문은 변하지 않는다**.
- `RunnableWithMessageHistory` 는 1.3.3에서 deprecated 되어 쓰지 않았다.

## 6. 프롬프트 (verbatim)
- `prompts/system_prompt.txt`(sha256 `13a28529…`, 8,371B)와 `prompts/human_prompt.txt`(sha256 `718e8ea1…`, 2,483B)를 **바이트 그대로** 사용한다. RCIF 재구성·few-shot·헤더 줄 삭제를 하지 않았고, `tests/test_prompts_verbatim.py` 9개가 이를 고정한다. sha 는 두 번 회전했다 — 모델 지식 경로를 더할 때, 그리고 context-only 제한을 걷어내고 web_search 도구 사용 지침을 넣을 때.
- system 은 리터럴 `SystemMessage` 로 넣어 템플릿 파싱을 거치지 않는다(중괄호가 생겨도 안전). human 은 `{question}`·`{context}` 2개만 치환된다.
- 토큰(o200k_base 실측): system **1,950**, human 템플릿 **534**, 고정 오버헤드 **2,484**.

### status 결정 표
| 조건 | status | LLM 호출 |
|---|---|---|
| 라우터가 `off_topic` | `out_of_scope` | 없음(거부 문장 바이트 고정) |
| 최신정보 필요 + 웹 비활성 + 스냅샷 없음 | `phase2_pending` | 없음 |
| 검색 abstain + 최신정보 없음 | `not_in_rulebook` | 없음 |
| 그 외 → 답변 생성 후 고정 거부 문장 검출 | `answered` / `not_in_rulebook` / `out_of_scope` | 1회 |

### `{context}` 블록 형식 (단일 조립점 `context.format_context`)
```
[자료 {i} | 2026 공식야구규칙 | {breadcrumb} | p.{page}]
[자료 {i} | 최신정보 | {label} | 기준일 {as_of} | 출처 {url} | 신뢰도 {confidence}]
```
원문 프롬프트에는 인용·기준일 지시가 없으므로, 모델이 기준일을 말할 수 있도록 **라벨에 기준일·출처를 넣는다**.

### 금지 목록
`.strip()`/`.format()`/dedent, 헤더 줄 삭제, 거부 문장 재작성, 시스템 메시지 앞 가변 텍스트 삽입, 두 번째 시스템 프롬프트로 답변 생성.

**개정(답변 스키마)**: 요청 파라미터(`response_format`)를 통한 형식 강제는 허용한다. 메시지를 조작하지 않기 때문이다. 이 주장을 말로 두지 않고 `tests/test_prompt_untouched_by_schema.py` 가 기계적으로 단언한다 — 스키마 on/off 에서 렌더된 메시지가 바이트 동일하고, 스키마 문자열이 메시지에 나타나지 않으며, bind 된 kwargs 에 메시지 관련 키가 없다.

## 6-A. 답변 스키마 (형식 강제)

프롬프트가 sha 로 동결되어 있어 형식 지시를 넣을 수 없다. 대신 OpenAI Structured Outputs 로 구조를 강제하고 **마크다운은 파이썬이 결정적으로 조립한다**. `with_structured_output` 은 `bind(response_format=…)` 만 하고 메시지를 건드리지 않으므로(`langchain_openai/chat_models/base.py`) 프롬프트 바이트·sha·골든 픽스처가 그대로다.

| 모듈 | 역할 |
|---|---|
| `src/baseball/answer_schema.py` | pydantic 정본 → strict JSON Schema. **필드 description 이 곧 형식 지시문이다**(실측 2,179토큰, 17필드) |
| `src/baseball/answer_render.py` | `AnswerDoc` → 마크다운. 섹션 순서·불릿·볼드가 여기서 결정된다 |
| `src/baseball/answer_lint.py` | 내용 검사. blocking 2종만 답변을 거부로 강등하고 나머지는 경고 |

**kind 별 섹션 순서** (빈 섹션은 생략)
- `term_rule`: 핵심답(굵게) → 정의 → **어떤 상황에서 적용되나요**(불릿) → **실제 경기에서는** → **왜 중요한가요**
- `situation`: 핵심답 → **판정** → **왜 이렇게 판정하나요** → **경기는 어떻게 되나요** → **상황이 달라지면** → **실제 경기에서는** → **왜 중요한가요**
- `entity` / `latest`: 핵심답 → (`latest` 만 기준일) → 사실 불릿 → **조금 더 설명하면** → **왜 중요한가요**
- 공통 말미: **다른 질문에 대해서는**(복합 질문의 하위 답변) → `※` 유의사항 → **근거**

**렌더러 불변식** — 거부는 `prompts` 의 상수 **바이트 그대로**만 낸다(부가 문구 0자). 덕분에 `detect_status` 의 40자 꼬리 예산 휴리스틱이 구조적으로 무력해지고, `detect_status`·`citations.extract`·`has_partial_refusal` 은 **한 줄도 바꾸지 않았다**. `**근거**` 섹션이 항상 규칙 번호를 본문에 남기므로 `citations.extract` 가 계속 작동한다.

**실패 처리** — 파싱·검증 실패(주원인은 출력 절단)면 `response_format` 없이 같은 메시지로 **딱 한 번** 재호출하고 `format_issues=["SCHEMA_FALLBACK"]` 로 남긴다. `raw.content` 는 반쪽 JSON 이라 쓰지 않는다. `ENABLE_ANSWER_SCHEMA=off` 로 레거시 평문 경로를 그대로 되살릴 수 있고, 이것이 품질 A/B 레버다.

**주의 두 가지** — `include_raw=True` 가 아니면 `AIMessage` 가 사라져 토큰·비용이 조용히 0 이 된다. 구조화 LLM 은 `streaming=False` 로 따로 만들어야 한다(생성자 `streaming=True` 는 `model_fields_set` 에 남아 `.invoke()` 조차 스트림 경로로 보낸다).

**대가** — 토큰 단위 스트리밍을 잃었다. 섹션 단위 `token` 이벤트로 쪼개 보내 SSE 계약(`route → status → sources → token* → final → done`)은 유지했고, UI 는 "답변을 구성하는 중…" 라벨로 대기를 알린다.

## 7. 검색 설계와 성능 (실측)
- 채널: exact(규칙번호 정확일치) + dense(pgvector cosine, top 20) + BM25(Kiwi 형태소, top 20) → RRF(k=60) → 조항 단위 parent expansion → 관련성 컷 → 최대 6건/3,000토큰.
- **관련성 컷**(`CONTEXT_MIN_SCORE_RATIO=0.55`, 신규): 융합 점수가 1위의 55% 미만인 문서를 제외한다. 무관한 자료가 섞이면 모델이 "확인할 수 없다"고 거부하는 현상이 실제로 관측되어 도입했다(같은 질문이 k=2에서는 정답, k=6에서는 거부).

| 베이스라인 | recall@6 |
|---|---|
| **RRF(하이브리드)** | **1.000** |
| dense 단독 | 0.923 |
| BM25 단독 | 0.923 |

**LLM 심판**(`evaluation/judge.py`, `--judge`) — 근거성·형식 준수·초보자 가독성·간결성 4축 1~5점. 심판 프롬프트는 이 모듈 안에만 있고 `prompts/` 를 건드리지 않는다. 심판이 실패해도 그 케이스만 비우고 평가를 멈추지 않는다.

**recall 분모 정정** — 예전에는 `expected_rule_refs` 가 빈 케이스가 `recall=1.0` 으로 분모에 들어가 평균을 부풀렸다(13건 중 2건이 무임승차). 이제 기대 조항이 있는 11건만 센다. **이 때문에 `evaluation/results/` 의 기존 수치와 직접 비교할 수 없다.**

**A/B** — 결과 파일명에 `_schema` / `_legacy` 접미사가 붙는다. `PROMPT_SHA` 는 이번 작업으로 바뀌지 않으므로 접미사가 없으면 두 판이 서로를 덮어쓴다.

## 11. 알려진 제약
- MinIO 고정 이미지(`RELEASE.2025-09-07`)는 CVE-2025-62506 미패치 → loopback·단일 계정·로컬 전용.
- Tavily 허용 도메인만으로는 결과가 0건인 경우가 있어, 1차 실패 시 도메인 제한 없이 재검색한다(출처 URL은 항상 표기).
- 포스트시즌 일정은 2026-09-15 기준 미발표이며, 스냅샷에 그 사실을 명시했다.
- `.streamlit/config.toml` 에는 `server.address`·`server.port` 를 두지 않는다. Streamlit Community Cloud 가 덮어쓴다고 문서화한 옵션은 다섯 개(`runOnSave`·`enableXsrfProtection`·`showErrorDetails`·`fastReruns`·`gatherUsageStats`)뿐이고 `server.address` 는 실제 소켓 바인딩이므로, 파일에 커밋하면 배포본이 루프백에만 묶여 플랫폼 헬스체크가 닿지 못한다. 로컬 루프백은 설정 우선순위(명령행 > 환경변수 > 파일)를 이용해 `make ui` 플래그로 강제하고 `test_server_binds_loopback` 이 양쪽을 단언한다.
- macOS에서 uv가 `.venv`의 `.pth`에 `UF_HIDDEN`을 설정하면 CPython이 그 파일을 건너뛴다. `bin/br` 래퍼가 플래그를 해제하고 `PYTHONPATH`로 이중 방어한다.

## 11-A. 메모리 실측과 배포 가능 범위 (2026-09-15 측정)

프로세스 상주 메모리를 단계별로 측정했다(macOS, Python 3.12, RSS 기준).

| 단계 | 상주 | 최대 |
|---|---|---|
| 인터프리터 | 11 MB | 11 MB |
| + streamlit·httpx (UI 전용 상한) | 52 MB | 52 MB |
| + FastAPI·LangChain·OpenAI 모듈 | 168 MB | 168 MB |
| + Kiwi 형태소 분석기 | 422 MB | 422 MB |
| + BM25 인덱스(701 청크) | 595 MB | 634 MB |
| 올인원(UI+백엔드 한 프로세스) | 600 MB | 626 MB |

Kiwi 로드가 254 MB, BM25 인덱스 빌드가 173 MB 로 전체의 대부분을 차지한다.
UI 는 `src/baseball/` 을 import 하지 않는 SSE 클라이언트이므로 52 MB 에 머문다.

Streamlit Community Cloud 한도는 메모리 690 MB~2.7 GB, CPU 0.078~2 코어이며 Docker 와 추가 인바운드 포트를
지원하지 않고 12시간 무트래픽 시 절전한다(공식 문서, 한도는 "2024-02 기준" 표기).
따라서 **배포를 막는 것은 메모리가 아니라 Postgres·MinIO 컨테이너**다. 상세 절차는 `docs/배포.md`.

의존성 해석은 엔트리포인트 디렉터리 → 저장소 루트 순이고 각 위치에서 `uv.lock` 이 최우선이므로,
`ui/requirements.txt` 를 엔트리포인트 옆에 두어 루트 `uv.lock` 보다 우선하게 했다(답변 경로 의존성만 담는다).
`ui/backend.py` 가 `API_BASE_URL` 유무로 모드를 고른다. 있으면 FastAPI 를 SSE 로 호출하고(로컬),
없으면 같은 프로세스에서 `RagService.stream()` 을 직접 호출한다(배포). 두 경로는 `(event, data)` 계약이 같다.

## 12-A. KBO 실데이터 (구현 완료)

키가 필요 없는 네이버 스포츠 공개 JSON 두 곳에서 순위와 일정을 읽고, 구단 기본 정보는 정적 파일로 둔다.
채팅 한 턴 안에서 처리하며 별도 페이지를 만들지 않았다.

### 소스와 확인된 함정

| 항목 | 내용 |
|---|---|
| 순위 | `/statistics/categories/kbo/seasons/{year}/teams`. 헤더 불필요. 승률은 승/(승+패)로 무승부를 제외한다(실측 최대 오차 0.000492) |
| 일정 | `/schedule/games`. `teamCode` 질의 인자는 무시되므로 클라이언트에서 거른다 |
| 정규시즌 필터 | `roundCode` 를 `kbo_r` 로 좁혀야 한다. 시범경기 `kbo_e`, 올스타 `kbo_as` 가 섞여 있고 올스타는 `EA`·`WE` 코드를 쓴다 |
| 취소 경기 | 우천 취소도 `statusCode` 는 `BEFORE` 로 남는다. `cancel` 을 함께 봐야 잔여 경기 수가 맞는다 |
| 경기 ID | `^\d{8}[A-Z]{2}[A-Z]{2}\d{5}$` 이고 앞 두 글자가 원정, 뒤 두 글자가 홈이다. 홈·원정 뒤바뀜을 공짜로 잡는다 |
| 선수 명단 | 키 없는 구단별 등록선수 엔드포인트가 없다. 리그 전체 상위 50명만 나오므로 명단으로 쓸 수 없어 보류했다 |
| 유튜브 | `youtube.com/robots.txt` 가 `Disallow: /feeds/videos.xml` 이다. 키 없는 RSS 경로가 막혀 Phase 1 에서는 보류했다. Phase 2 에서 **업로드 재생목록**(`playlistItems.list`, 1 unit)으로 열었다 — `src/baseball/highlights.py` |

### 설계 결정

- **DDL 을 바꾸지 않았다.** 기존 `source_snapshots(kind, payload jsonb, as_of, fetched_at)` 와 그 인덱스가 그대로 캐시 저장소다. 운영 중인 원격 데이터베이스를 건드리지 않는 것이 가장 강한 안전장치다.
- **정규화한 결과를 저장한다.** 원본 응답이 아니라 모델을 통과한 축약본을 넣어 행 크기를 10분의 1로 줄였다. `kind` 별로 최근 3건만 남긴다.
- **라우터의 `kind` 는 그대로 네 값이다.** 주제·구단 태그를 직교하는 필드로 더했고 `to_dict()` 도 두 키 그대로라 API 응답과 골든셋 계약이 바뀌지 않는다. `off_topic` 에는 태그를 붙이지 않아 거부 경로가 데이터 조회로 새지 않는다.
- **프롬프트는 건드리지 않았다.** KBO 블록은 `format_context` 한 곳에서만 조립되며 기존 블록 형식을 그대로 쓴다.
- **실패는 사용자 경로로 올라가지 않는다.** 조회 실패 시 저장본으로 물러나고, TTL 을 넘긴 저장본은 "오래된 저장본" 상태로 컨텍스트와 출처 칩에 그대로 드러낸다. 상류 스키마 변경은 전송 실패와 구분해 별도 예외로 기록한다.
- **새 의존성과 새 비밀 키가 없다.** 배포 메모리 예산이 그대로다.

### 불변식

모델에 20개를 걸어 상류의 조용한 변경을 즉시 드러낸다. 구단 코드 집합, 순위 1~10 순열, 승패합과 경기수 일치,
승률 정의, 리그 전체 승수와 패수 일치, 정규시즌 여부, 경기 ID 형식과 홈·원정 교차 검증, 날짜와 일시 일치,
시작 전 경기의 점수 부재, 상태 코드 체계 등이다. 테스트는 성립뿐 아니라 **깨질 때 실제로 터지는지**도 확인한다.

## 12-B. 구단 정보와 선수 명단 (구현 완료)

### 선수 데이터

상류에 구단별 등록선수 엔드포인트는 없지만 `pageSize=500` 으로 시즌 기록 목록 전체를 받을 수 있다.
1000 이상을 주면 조용히 0건이 되므로 이 값이 사실상의 상한이다. `teamId` 와 `page` 인자는 무시된다.

받은 결과를 `data/kbo_players.jsonl` 에 한 줄 한 명으로 저장하고 앱은 그 파일만 읽는다.
첫 줄은 언제 어디서 받았는지 적은 메타다. 재생성은 `python -m baseball.kbo_players build`.

| 항목 | 값 |
|---|---|
| 선수 | 581명 |
| 파일 | 246 KB |
| 상주 메모리 | 약 1.5 MB |

**중복 함정.** 상류는 타석에 한 번이라도 선 투수를 타자 목록에도 넣는다. 그대로 두면 62명이 두 번
실리고 한 선수가 카드의 양쪽 탭에 모두 나타난다. 소속은 목록이 아니라 포지션으로 정한다.

입문자 대상이므로 WAR·wOBA·wRC+ 같은 파생 지표는 담지 않는다. 이닝은 `138 2/3` 형태의 문자열이라
정렬용 숫자를 함께 저장한다.

### 구단 상징색

10개 구단 색을 각 구단 공식 웹사이트 스타일시트에서 직접 확인했다. 로고·워드마크·엠블럼·구단 서체는
쓰지 않으며 색상값만 사용한다. 구단 식별은 이름 텍스트로 한다. 적색 계열이 일곱이라 색만으로는
구분이 되지 않기 때문이기도 하다.

  올리는 방식은 폐기했다. 세 구단이 비슷한 파랑으로 수렴해 서로 구분이 되지 않는다.

어긋나면 실패하므로 데이터가 낡으면 드러난다.

## 12. Phase 2 확장 지점
- 도구 인터페이스(`ToolResult{text, sources, retrieved_ids}`)를 이미 `@tool` 로 맞춰 두어, 도구만 추가하면 된다.
- 응답의 `freshness` / `needs_web` / `status=phase2_pending` / `route` 가 Phase 2 라우팅 신호다.
- 데이터 소스 제약(조사 결과): koreabaseball.com은 robots `Disallow: /` 로 직접 수집 금지. 네이버 스포츠 `api-gw` 는 키 없이 순위·일정·선수 조회가 가능하나 비공개 API이므로 스냅샷 우선 + 스키마 검증 + stale 폴백이 필요하다. YouTube는 `search.list`(100회/일) 대신 업로드 재생목록(1유닛)을 쓰고, 저장한 API 데이터는 30일 내 갱신·삭제해야 한다. **구현됨** — `data/kbo_youtube_channels.json`(10구단 + 리그 공식) → `youtube.fetch_playlist_items`(1 unit) → `youtube.fetch_video_details`(1 unit) 검증. 홈 → 원정 → 리그 순으로 보되 한 건이라도 맞으면 멈추므로 흔한 경우 2 units 다. 한때 이 자리를 Tavily 일반 웹 검색이 대신했는데, 상위 5건에 youtube.com 주소가 섞이기를 기다리는 구조라 회수가 사실상 0 이었다. 30일 의무는 `assistant_cache` 의 행별 TTL 과 `python -m baseball.highlights purge` 로 지킨다.
